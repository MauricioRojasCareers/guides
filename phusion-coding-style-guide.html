Coding style, without the wall of rules

The rules you are most likely to need while writing C++ and Qt code. Use this to develop good instincts, then consult the repository documents when a detail matters.

Which rule wins?
  1. The current task and reviewer direction.
  2. The repository's current CLAUDE.md and docs/standards/.
  3. The repository's .clang-format.
  4. The internal Coding Standards wiki and Qt Coding Style.

The wiki still mentions C++17. The current repository says C++23, so C++23 is the rule. Likewise, let .clang-format settle formatting disagreements.

The golden 12

1
Be explicit.

Readable, unsurprising code normally beats compressed or clever code. Clever code needs both a technical reason and a useful reference.

2
Use exact-width integers.

Write int32_t, uint16_t, and friends. Do not use int or Qt's qint* aliases.

3
Avoid auto.

Spell out meaningful types. Never bind an Eigen expression to auto; use a concrete Eigen type or call .eval().

4
Make units visible.

Use typed wrappers and named conversions such as Angled::fromRadians(x).toDegrees(). Do not hand-roll conversion ratios.

5
Use const.

Apply it to methods, parameters, and locals when possible. Do not return const T by value.

6
Prefer references.

Use a pointer only when null is meaningful or an API requires one. Use smart pointers for ownership.

7
Name behavior.

No default arguments. Avoid boolean behavior switches; use a small enum. A single-property setter may take a bool.

8
Keep records labeled.

Small data-only structs should remain aggregates with typed members. Construct them with C++23 designated initializers.

9
Fail loudly.

Do not replace a throw, assert, or strict parse with a silent fallback. Throw std::runtime_error; include QFile::errorString() for file failures.

10
Use modern iteration.

Prefer range loops and standard algorithms when the index has no meaning. Never use a default-reference lambda capture such as [&].

11
Comment the why.

Document purpose, assumptions, units, edge cases, and non-obvious decisions. Do not narrate the syntax or leave project-phase commentary behind.

12
Format mechanically.

Four spaces, a 120-column limit, and the repository formatter. Do not spend judgment on spacing that the tool owns.

Patterns you will use

Types, construction, and units

// Avoid: vague types, positional slots, and raw unit math
auto orientation = EulerAngles(yaw, pitch, roll);
double degrees = radians * 180.0 / M_PI;

// Prefer: explicit types, labeled fields, and named unit conversion
const EulerAngle3::YawPitchRoll<double> orientation{
    .yaw = yaw,
    .pitch = pitch,
    .roll = roll,
};
const double degrees = Angled::fromRadians(radians).toDegrees();

Function interfaces

// Avoid: the call site cannot explain true or the omitted value
void exportCloud(bool compact, int quality = 4);
exportCloud(true);

// Prefer: the call site says what it means
enum class CloudLayout { compact, full };
void exportCloud(CloudLayout layout, int32_t quality);
exportCloud(CloudLayout::compact, 4);

Loops and captures

// Avoid
for (size_t i = 0; i < receptors.size(); ++i) {
    process(receptors[i]);
}
runAsync([&] { update(result); });

// Prefer
for (const CameraReceptor &receptor : receptors)
    process(receptor);
runAsync([this, &result] { update(result); });

Error handling

// Avoid: execution continues after an invalid state
if (!file.open(QIODevice::ReadOnly)) {
    TRACE("open failed");
    return {};
}

// Prefer: preserve the useful failure reason
if (!file.open(QIODevice::ReadOnly))
    throw std::runtime_error(
        QString("cannot open %1 for reading: %2")
            .arg(file.fileName(), file.errorString()).toStdString());

Documentation that helps

  • Explain why a class or struct exists and when it should be used.
  • For a method, document parameters, return value, valid ranges, units, preconditions, postconditions, and important edge cases.
  • Explain magic values and assumptions. For a workaround, include the issue reference and the technical reason.
  • Put comments above the code. Trailing comments are mainly for units or short row labels.
  • Write exception messages in lowercase, present tense, with no ending punctuation: cannot open file foo.csv for reading.
  • Write plainly to a colleague. Do not use em dashes, banner-divider comments, invented abstraction labels, or status narration such as “Phase 2 implementation.”

From edit to merge request

  1. Start from the issue. Name the branch with the issue number followed by a short version of the issue title.
  2. Keep the change focused. Remove temporary notes and explain the final design, not the history of arriving there.
  3. Format changed C/C++ files.
    clang-format -i path/to/file.cpp path/to/file.h
  4. Build and test in the Resolute container. Use the Docker development guide for the exact mount and build commands.
  5. Review the diff.
    git diff --check
git diff
  6. Commit in the imperative mood. Read the subject as: “If applied, this commit will …” Use your Phoenix LiDAR email identity.
  7. Open a merge request. Put the issue first in the title, for example #1234 fix stale calibration display. The pipeline must pass without new warnings.
Cloud and AI tools: the internal wiki warns against tools that submit source code to cloud services. Before using an AI assistant, cloud formatter, or cloud analyzer on company code, confirm the currently approved policy and configuration with your manager or security owner.

The 60-second pre-review checklist

  • No plain int, Qt integer aliases, unexplained auto, or Eigen expressions bound to auto.
  • Units use typed wrappers and named conversions; persisted or network structs have a static_assert on size.
  • No default arguments, ambiguous boolean switches, raw owning pointers, C-style casts, qBound, or default-reference lambda captures.
  • Members are initialized at declaration; nullable pointers start at nullptr; everything reasonable is const.
  • Failures are visible and actionable; every QFile error reports errorString().
  • Comments explain purpose and decisions, not syntax, phases, or the process that produced the code.
  • clang-format, the build, relevant tests, and git diff --check pass.
