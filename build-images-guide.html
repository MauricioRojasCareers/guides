PHOENIX LIDAR SYSTEMS

Building the Yocto images

A practical guide to building CM4, CM5, SOM, and x64 images from buildimage-yocto.

What this builds: deployable Phoenix Linux system images. The neighboring buildimage-generic repository only creates a legacy Ubuntu 18.04 development container; it is not used by this procedure.

1Prepare the build host

Use a Linux host with ample free disk space, RAM, and CPU time. Install Git, Docker Engine, and an SSH client. Your user must be able to run docker. The build itself runs in the pinned Siemens kas 3.2 container, so kas does not need to be installed on the host.

git --version
docker --version
docker run --rm hello-world

If the Docker test requires sudo, configure your account for Docker or run the build from an account that already has access. The repository scripts invoke docker directly.

2Verify private GitLab access

The build fetches Phusion and its submodules through SSH. Ensure your key is present under ~/.ssh, registered with GitLab, and authorized for the Phoenix repositories.

ssh -T git@gitlab.com
git ls-remote git@gitlab.com:phoenixlidar/phusion.git master

The second command should print a commit ID for master. Fix access before starting a long image build.

3Enter the repository and select the software revision

cd /home/mauricio/1playground/buildimage-yocto

# Required: branch containing the Phusion/Rover source
export PHUSION_BRANCH=master

# Optional: pin a tag or full commit. If omitted, the branch tip is used.
# export PHUSION_COMMIT=9.0.0
# export PHUSION_COMMIT=0123456789abcdef0123456789abcdef01234567

For a reproducible release, set both variables. With only PHUSION_BRANCH, rebuilding later may select a newer commit.

To build all four sequentially:

export PHUSION_BRANCH=master
./build.sh

The first build downloads and compiles a large dependency set. Later builds reuse the repository-level downloads/ and sstate-cache/ directories.

5Find the outputs

Normal Yocto deploy output is under the selected build directory:

build-<target>/tmp/deploy/images/phoenixlidar-<target>/

The build also copies release-ready files into:

artifacts/

Artifact filenames include the Rover version, Yocto commit, Phusion commit, and branch. List the newest results with:

find artifacts -maxdepth 1 -type f -printf '%TY-%Tm-%Td %TH:%TM  %f\n' | sort -r

# Example: inspect one machine's raw deploy output
find build-cm4/tmp/deploy/images/phoenixlidar-cm4 -maxdepth 1 -type f -printf '%f\n' | sort
TargetRelease outputs to expect
CM4 / CM5.mender, .sdimg.zst, .sdimg.bmap, recovery .wic, .rvdbg.zst
SOM / x64.mender, .hddimg, .rvdbg.zst
Additional raw deploy outputUEFI VMDK and, for x64, HDD-image bmap output

6Choose the correct artifact

  • .mender: update an already-running compatible unit through Mender.
  • .sdimg.zst + .sdimg.bmap: provision CM4/CM5 storage.
  • Recovery .wic: create an RPi recovery device that restores the embedded system image.
  • .hddimg: create bootable installer media for SOM/x64 targets.
  • .rvdbg.zst: unstripped Rover symbols for diagnosing crashes; it is not boot media.
Destructive operation: writing an SD, eMMC, USB, WIC, or HDD image overwrites the selected block device. Resolve the exact device with lsblk, unmount its partitions, and verify it again before writing. Recovery media can overwrite a target automatically when booted; remove unrelated storage first.

Useful developer workflow

To run a BitBake command inside the correctly configured kas environment without rebuilding the complete image:

export PHUSION_BRANCH=master
./build_yoctoshell.sh configs/poky-scarthgap-cm4.yml \
  'bitbake phoenix-rover -c compile'

Replace the config with the desired target. Other useful Rover tasks include -c cleansstate, -c compile, and -c install. A full image build remains the release verification step.

Troubleshooting checklist

  1. Confirm PHUSION_BRANCH is exported in the same shell.
  2. Repeat the git ls-remote test to distinguish SSH failures from Yocto failures.
  3. Confirm Docker runs without interactive privilege prompts.
  4. Check free space with df -h . /opt.
  5. Read the first real ERROR: in the log; later failures are often consequences.
  6. Retry the same build command after a transient download failure. Shared downloads and completed work are retained.

Source of truth: the Scarthgap kas configurations and build scripts in buildimage-yocto. This guide intentionally does not use the older Kirkstone command examples still present in that repository's README.
