SpatialExplorer field guide

Qt development in Phusion

A working map of the Qt concepts you need to change SpatialExplorer confidently. This guide follows the repository as it exists: Qt 6.5+, C++23, CMake, Qt Widgets, Designer forms, and a large event-driven desktop application.

Keep both companion guides nearby. Use Phusion with Docker for the build and runtime environment, and Phusion coding style for project-specific C++ rules. This page teaches the Qt layer.

The mental model

The event loop

QApplication::exec() waits for mouse, keyboard, timer, socket, and queued-signal events. A long slot blocks all GUI activity.

QObject

Qt's runtime object: identity, parent ownership, properties, signals, slots, thread affinity, and deferred deletion.

QWidget

A visible QObject. SpatialExplorer composes dialogs, dock widgets, toolbars, views, and custom OpenGL widgets.

Signals and slots

Typed event delivery between objects. The sender announces; receivers choose how to react.

Meta-object compiler

moc generates support for Q_OBJECT. CMake's AUTOMOC runs it for repository targets.

Designer and uic

A .ui file describes a widget tree. uic generates ui_name.h; never edit that generated header.

Your first real task: change or add a dialog

  1. Find a nearby dialog that behaves similarly. Use its structure, but do not copy legacy style violations.
  2. Edit the .ui form in Qt Designer. Give widgets descriptive object names such as pushButtonImport or comboBoxCoordinateSystem.
  3. Create or update the matching lowercase .h and .cpp files.
  4. Make the class inherit the appropriate widget and add Q_OBJECT when it declares signals, slots, or other meta-object features.
  5. Include the generated ui_dialogname.h only in the implementation file and call ui->setupUi(this).
  6. Connect UI signals using the typed function-pointer syntax.
  7. Add new sources or special headers to the relevant CMake source list. Header-only Q_OBJECT classes must be listed so AUTOMOC sees them.
  8. Build the narrowest target, run it, and exercise success, invalid input, cancel, close, and repeated-open paths.
// dialogimportsettings.h
#pragma once

#include <QDialog>

namespace Ui { class DialogImportSettings; }

class DialogImportSettings : public QDialog {
    Q_OBJECT

    Ui::DialogImportSettings *mUi = nullptr;

  public:
    explicit DialogImportSettings(QWidget *parent = nullptr);
    ~DialogImportSettings() override;

  signals:
    void settingsImported(const QString &fileName);
};

// dialogimportsettings.cpp
#include "dialogimportsettings.h"
#include "ui_dialogimportsettings.h"

DialogImportSettings::DialogImportSettings(QWidget *parent)
    : QDialog(parent), mUi(new Ui::DialogImportSettings) {
    mUi->setupUi(this);
    connect(mUi->pushButtonImport, &QPushButton::clicked, this, [this] {
        emit settingsImported(mUi->lineEditFileName->text());
    });
}

DialogImportSettings::~DialogImportSettings() { delete mUi; }
Ownership detail: widgets created by setupUi() become children of the dialog and Qt deletes them with the parent. The generated Ui::... helper itself is not a QObject, so a raw allocated helper must be deleted explicitly. Match the established pattern in the specific area you edit.

Signals and slots you can reason about

// Preferred: compile-time checked names and types
connect(mTimer, &QTimer::timeout,
        this, &SensorWidget::refreshStatus);

connect(mUi->checkBoxEnabled, &QCheckBox::toggled,
        this, [this](const bool enabled) {
            mController.setEnabled(enabled);
        });
  • A signal is a notification, not a command. Name it for what happened: settingsChanged, not doUpdateSettings.
  • Give a context object for lambdas, normally this. Qt then disconnects the lambda when the context is destroyed.
  • Capture only what the lambda needs. Phusion lint rejects [&]; write [this, &result] or capture a safe value.
  • Use QOverload<...>::of(...) when a Qt signal is overloaded.
  • A connection does not copy the receiver's lifetime. Be especially careful when a lambda captures raw pointers or references to short-lived locals.
  • Let Qt::AutoConnection handle ordinary same-thread connections. Specify a connection type when thread behavior is intentional.

Threading: the rule that prevents most crashes

Only the GUI thread touches widgets. Never read or mutate a QWidget from a worker thread. Send data back with a queued signal or QMetaObject::invokeMethod(..., Qt::QueuedConnection).

A QObject “lives” in one thread. Its queued slots run through that thread's event loop. Moving a worker object with moveToThread() changes its affinity; the QThread object itself still lives in the thread that created it.

QThread *thread = new QThread(this);
Worker *worker = new Worker;             // no parent, so it can move
worker->moveToThread(thread);

connect(thread, &QThread::started, worker, &Worker::process);
connect(worker, &Worker::progress, this, &ProgressDialog::setProgress,
        Qt::QueuedConnection);
connect(worker, &Worker::finished, thread, &QThread::quit);
connect(worker, &Worker::finished, worker, &QObject::deleteLater);
connect(thread, &QThread::finished, thread, &QObject::deleteLater);
thread->start();
  • Do not run expensive LiDAR processing, blocking I/O, or long loops in a GUI slot.
  • Create timers and sockets in the thread where they will be used.
  • Use deleteLater() for a QObject owned by another running event loop.
  • A direct connection across threads executes in the emitter's thread and is usually unsafe. Treat it as an exceptional, documented choice.
  • A blocking queued connection can deadlock. Never use it between objects in the same thread.

Ownership, lifetime, and pointers

  • When you create a QObject with a parent, the parent deletes it. This is why new QTimer(this) is normal Qt code.
  • Do not combine parent ownership with a second owning smart pointer.
  • A raw pointer to a parent-owned widget is non-owning. Initialize it to nullptr and make the ownership obvious.
  • Use QPointer<T> when a non-owning QObject pointer can outlive the object; it becomes null when the object is destroyed.
  • For non-QObject ownership, follow ordinary C++: values first, then std::unique_ptr, and std::shared_ptr only for genuine shared lifetime.
  • A modal stack dialog such as QMessageBox box(this) is fine. A heap dialog should have a clear parent or explicit owner.

Models, views, and delegates

For a tiny, local list, a convenience widget such as QListWidget can be enough. For domain data, large tables, shared data, sorting, filtering, or more than one presentation, use the model/view family.

ResponsibilityQt pieceQuestion it answers
Data and rolesQAbstractItemModel, QStandardItemModelWhat exists, and what value does each cell expose?
PresentationQTableView, QTreeView, QListViewHow is the model navigated and displayed?
Cell rendering/editingQStyledItemDelegateHow does one value look and how can it be edited?
Sorting/filteringQSortFilterProxyModelHow do I transform a view without duplicating source data?

When a model changes, use the correct begin/end notification pair or emit the appropriate dataChanged range. A view cannot infer that your backing container changed.

CMake and generated-code traps

  • SpatialExplorer requires Qt 6.5 or newer and links modules including Core, Gui, Widgets, OpenGL, Network, Sql, Svg, Concurrent, Test, Multimedia, and WebEngineWidgets.
  • Do not edit ui_*.h, moc_*.cpp, or generated resource files. Change their source files.
  • If adding Q_OBJECT produces “undefined reference to vtable,” first confirm the header is visible to AUTOMOC and is in the target's source list.
  • If ui_dialog.h is missing, confirm the .ui file is in FILELIST_UI_AUTO or the relevant UI list, then rerun CMake.
  • If a resource path fails, inspect embeddedfiles.qrc and use the compiled resource prefix, not a source-tree filesystem path.
  • Link a new Qt API through its target, for example Qt6::Network. Including a header alone does not link the module.

A debugging ladder

  1. Read the first build error. Generated-code failures often cause a page of secondary errors.
  2. Check the object name. If mUi->button is missing, inspect the widget's Designer objectName.
  3. Verify the connection. Store the returned QMetaObject::Connection or assert the result when diagnosing a suspicious connection.
  4. Verify the thread. Compare QThread::currentThread() with object->thread().
  5. Inspect ownership. Use dumpObjectTree() and dumpObjectInfo() when widgets disappear, leak, or receive events unexpectedly.
  6. Check the event loop. If the window freezes, pause in the debugger and find the long-running GUI-thread call.
  7. Reduce the path. Reproduce with the smallest dialog, data file, or action sequence before changing architecture.

Practice path

  1. Change text or layout in one existing .ui file, rebuild, and find the result.
  2. Add a button and connect its signal to a short lambda.
  3. Add a field, validate it, and show a useful QMessageBox on invalid input.
  4. Trace an existing signal from emitter to receiver and identify the connection type.
  5. Find one worker object and diagram its thread affinity, startup, result delivery, and deletion.
  6. Add or modify a small model-backed view and test its change notifications.
  • The GUI remains responsive during work.
  • Every QObject has understandable ownership and thread affinity.
  • Connections use typed syntax, a context object, and explicit safe captures.
  • Generated files remain untouched and CMake knows about new sources.
  • Error and cancel paths have been exercised, not just the happy path.
  • The change follows the Phusion coding-style checklist and passes the container build.
