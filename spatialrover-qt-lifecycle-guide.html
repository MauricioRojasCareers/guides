Qt lifecycle for a headless embedded service

Rover uses Qt without a GUI. Its event loop coordinates timers, sockets, serial ports, child processes, Unix signals, worker threads, and controlled shutdown.

One process, one main event loop

main()install signal bridge
Roverconstruct + connect
exec()dispatch events
quit()leave loop
destructorsfinal cleanup

Rover derives from QCoreApplication. Before exec(), constructors can create objects and connections, but queued work and zero-delay timers wait for the loop. This is why the code uses QTimer::singleShot(0, ...) for initialization that must happen after callers finish wiring signals.

Event sources

Timers, serial readyRead, network sockets, QProcess output, queued signals, and QSocketNotifier all become callbacks on an event loop.

Run-to-completion

A slot runs until it returns. While it runs, that thread's loop cannot dispatch another ordinary event.

Deferred work

Queued signals, posted events, zero-delay timers, and deleteLater() defer work to a compatible event-loop turn.

Nested loops

Manual processEvents() and nested event loops permit reentrancy. Prefer asynchronous state machines or workers.

Thread affinity, not object location

Every QObject has an owning thread. Queued events execute in that thread. A QThread object normally belongs to its creator's thread, while QThread::run() executes in the managed thread. That distinction explains many surprising bugs.

OperationWhere it executes
Direct method callThe caller's current thread, regardless of the target QObject's affinity.
Direct connectionImmediately in the emitter's thread.
Queued connectionLater in the receiver's affinity thread, through its event loop.
QThread::run()The new managed thread.
Method called on a normal QThread objectThe calling thread; the QThread object usually lives with its creator.
deleteLater()Deferred through the object's event loop, or when its thread finishes.

Preferred worker pattern

QThread *thread = new QThread(this);
Worker *worker = new Worker;              // no parent before move
worker->moveToThread(thread);
connect(thread, &QThread::started, worker, &Worker::start);
connect(worker, &Worker::resultReady, this, &Rover::consumeResult,
        Qt::QueuedConnection);
connect(worker, &Worker::finished, thread, &QThread::quit);
connect(worker, &Worker::finished, worker, &QObject::deleteLater);
connect(thread, &QThread::finished, thread, &QObject::deleteLater);
thread->start();
Study existing code critically. Rover contains older classes that subclass QThread and even move the QThread object to itself. Learn what they do, but use current Qt guidance and reviewer direction for new designs. Repository presence proves compatibility, not preferred style.
  • Create a timer, socket, or serial port in the thread that will use it.
  • A QObject with a parent cannot move to another thread; its children move with it.
  • Do not delete an active QObject from another thread. Arrange shutdown and use deleteLater().
  • Keep high-rate read callbacks short. Buffer or hand off work without blocking the device.
  • Use explicit captures. A queued lambda may execute after captured stack variables are gone.

Unix signals safely enter Qt

POSIX signal handlers can call only async-signal-safe functions. Rover uses the standard self-pipe/socket-pair pattern:

SIGTERMfrom systemd
signal handlerwrite one byte
QSocketNotifierfd readable
Qt slotrequest shutdown

The tiny handler writes to a socket pair. QSocketNotifier converts descriptor readiness into a normal Qt callback, where Rover can safely invoke QObject code. Avoid logging, allocating, locking ordinary mutexes, or calling arbitrary Qt APIs inside a POSIX handler.

SpatialRover shutdown is a protocol

  1. A network command, power request, or Unix signal calls slotRequestShutDown().
  2. Rover marks shutdown requested, sends final status/component information, and confirms the request.
  3. Camera, LiDAR, and generic recorder managers receive shutdown requests.
  4. Each manager stops acquisition, flushes/finishes its writers, and reports readiness.
  5. slotTryShutdown() returns until every existing manager is ready.
  6. If requested, Rover powers sensors off.
  7. A short delayed QCoreApplication::quit() lets final messages escape.
  8. The main loop returns; Rover's destructor tears down remaining components in a deliberate order.
  9. systemd waits up to its stop timeout, then may use SIGKILL. Forced termination skips graceful cleanup.
Do not replace coordinated shutdown with exit() or kill -9. Those paths can skip recorder flushing, file finalization, sensor power handling, and destructors. SIGKILL is a last-resort recovery action, not a normal workflow.

Design a component for clean lifecycle

  • Construction establishes invariants but does not assume the event loop has already run.
  • start() is idempotent or rejects duplicate startup clearly.
  • Callbacks are bounded and never hold the event loop hostage.
  • Errors transition to an explicit state and do not create reconnect storms.
  • requestStop() stops new work, cancels timers/I/O, and begins draining.
  • A completion signal means resources are actually safe to destroy.
  • Destruction cannot race queued callbacks or a running thread.

Debug lifecycle failures

SymptomAsk
Timer never firesWas it created in a thread with a running event loop? Is that loop blocked?
Slot runs in wrong threadWhat is sender thread at emission, receiver affinity, and connection type?
Random shutdown crashAre queued callbacks reaching an object after dependencies were destroyed?
Service takes 30 seconds to stopWhich recorder never signaled readiness? Which thread or process is still blocking?
Immediate restart after stopDid systemd's Restart=always apply? Was a true service-stop action requested?
Watchdog firesWhich main-thread callback exceeded the interval? Was there blocking I/O or heavy computation?
Duplicate activity after reconnectWere old signal connections, timers, or device objects disconnected and destroyed?

Useful observations include thread IDs in logs, object->thread(), process and thread listings, a debugger backtrace of every thread, and timestamps around state transitions.

  2. Find every zero-delay timer in Rover and explain why direct construction-time execution would differ.
  3. Trace SIGTERM from systemd into slotHandleSignal().
  4. Draw the shutdown readiness graph for all three recorder managers.
  5. Study WatchDog: identify its affinity, timer's thread, ping receiver, and failure action.
