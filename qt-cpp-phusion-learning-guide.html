Follow-along learning path · six sessions

Learn C++ through Qt and Phusion

A practical starting point for an experienced programmer learning C++. Build something small, understand why it works, then recognize the same patterns in SpatialExplorer and Rover.

Your route: one concept, one experiment, one real file

You already know how to program. Start building with Qt now, while deliberately learning the C++ rules that determine whether your program is correct. Spend 45–90 minutes per session. Predict the output, run the example, change it, and explain the result before moving on.

Qt is much more than a GUI library. SpatialExplorer uses Qt Widgets and Designer forms; Rover uses timers, event loops, networking, and device communication. The exercises below build a simulated sensor dashboard that connects these two sides without requiring hardware.

1. Learn values before objects with parents

values.cpp

#include <QDebug>
#include <QString>
#include <vector>

struct Reading {
    QString name;
    double temperature = 0.0;
};

bool isHot(const Reading &reading) {
    return reading.temperature >= 30.0;
}

int main() {
    const std::vector<Reading> readings{{"front", 24.5}, {"rear", 31.0}};
    for (const Reading &reading : readings) {
        qInfo().noquote() << reading.name << reading.temperature
                          << (isHot(reading) ? "HOT" : "OK");
    }
}

Run ./build/values. Expect front 24.5 OK and rear 31 HOT. The struct groups data; each Reading is a value. The vector owns its elements and releases its storage when it goes out of scope. This deterministic cleanup is part of RAII: tie a resource’s lifetime to an object’s lifetime.

SyntaxWhat it means here
const Reading &readingBorrow an existing Reading without copying it; this reference cannot modify it. The original must remain alive.
reading.temperatureAccess a member through a value or reference.
std::vector<Reading>A template instantiated as a resizable collection of Readings.
QStringA Qt text value. It is copyable; QObject is not. You do not need an application event loop for this simple text operation.

Try it

  1. Add a sensor at exactly 30 °C. Predict its classification.
  2. Change the threshold into a second function parameter.
  3. Make a copy of a Reading, change the copy, and print both. Does the original change?
Checkpoint answer

30 is HOT because the comparison includes equality. A copied Reading has independent value semantics. References borrow the original; they do not make a copy or extend its lifetime in this parameter example.

Phusion connection: open spatialexplorer/dialogviewtraces.cpp. Find std::deque<std::pair<TimePoint, QString>> lastN and the “make a copy” comment. Each pair holds a time and text; the dialog removes entries from its local copy while populating the view.

2. Let the event loop call your code

heartbeat.cpp

#include <QCoreApplication>
#include <QDebug>
#include <QTimer>

int main(int argc, char *argv[]) {
    QCoreApplication app(argc, argv);
    QTimer timer;
    int count = 0;
    QObject::connect(&timer, &QTimer::timeout, &app, [&count, &app] {
        qInfo() << "tick" << ++count;
        if (count == 5) {
            app.quit();
        }
    });
    timer.start(500);
    return app.exec();
}

Run ./build/heartbeat. Expect ticks 1 through 5, roughly half a second apart, followed by exit. exec() keeps main active while Qt dispatches events; it returns after quit. A timer schedules notifications; it is not a new thread and its interval is not a precision timing guarantee.

start(500)Register timer
app.exec()Dispatch events
timeoutInvoke lambda
quit()End event loop

&timer takes an object’s address; &QTimer::timeout names a member function. [&count, &app] captures two existing local objects by reference. Both remain alive until the event loop returns. The &app argument before the lambda is its Qt context, which controls connection lifetime and queued execution context.

Try it

  1. Change the interval to 100 milliseconds and stop at 10 ticks.
  2. Print a message immediately before and after app.exec(). Predict the order.
  3. Temporarily replace return app.exec(); with return 0;. Why are there no ticks?
Checkpoint answer

The “after” message appears only after quit. Without the event loop, main returns before timeout events can be delivered. A reference capture is appropriate here because the locals outlive every callback invocation; a function returning while a callback still retains references to its locals would leave dangling references.

Phusion connection: read rover/powerbutton.cpp, searching for mTimerCheckEvents. Its constructor connects timeout to eventRead and starts a 100 ms timer when initialization succeeds. Find its member declaration in powerbutton.h. Read this as a timer example; the actual class also manages Linux device and D-Bus resources.

3. Give your sensor an identity

sensor.h

#pragma once
#include <QObject>
#include <QTimer>

class Sensor : public QObject {
    Q_OBJECT

  public:
    explicit Sensor(QObject *parent = nullptr);
    void start();
    void stop();

  signals:
    void readingChanged(int sequence, double temperature);

  private:
    QTimer *mTimer = nullptr;
    int mSequence = 0;
};

sensor.cpp

#include "sensor.h"

Sensor::Sensor(QObject *parent) : QObject(parent), mTimer(new QTimer(this)) {
    mTimer->setInterval(500);
    connect(mTimer, &QTimer::timeout, this, [this] {
        ++mSequence;
        const double temperature = 20.0 + (mSequence % 20);
        emit readingChanged(mSequence, temperature);
    });
}

void Sensor::start() { mTimer->start(); }
void Sensor::stop() { mTimer->stop(); }

The header declares the interface; the cpp defines its behavior. Sensor::start means “start belonging to Sensor.” public QObject is inheritance: Sensor gains Qt object behavior. explicit prevents using this constructor as an implicit conversion from a parent pointer. The initializer list constructs the base and initializes members before the constructor body runs.

mTimer is a pointer. mTimer->start() accesses the pointed-to object. new QTimer(this) makes the Sensor its Qt parent, so destroying the Sensor deletes the timer. This is a specific ownership rule, not a property of raw C++ pointers in general. The lambda captures this, a pointer to this Sensor; the Sensor is also the connection context.

Q_OBJECT enables the generated meta-object features needed by our signal. Declare readingChanged in the header and emit it in the cpp; moc supplies its implementation. A receiver can be an ordinary member function such as start, without a slots: declaration when using typed connect. Signals do not inherently create asynchronous work: same-thread automatic connections normally invoke receivers immediately. Qt signals and slots.

Try it

  1. Change the generated temperature range to 10–29 °C.
  2. Add a reset() method that sets mSequence to zero. Decide whether it also emits a reading, then explain your choice.
  3. Temporarily remove sensor.h from CMake’s source list and investigate any moc issues; restore it afterward. Exact discovery behavior can depend on includes.
Checkpoint answer

The sequence persists across stop/start because stop only stops the timer. A reset that emits a new reading is a different API from a reset that merely changes the next generated reading. Neither needs a thread.

4. Wire a small dashboard together

main.cpp

#include "sensor.h"
#include <QApplication>
#include <QLabel>
#include <QPushButton>
#include <QStringList>
#include <QTimer>
#include <QVBoxLayout>
#include <QWidget>

int main(int argc, char *argv[]) {
    QApplication app(argc, argv);
    QWidget window;
    window.setWindowTitle("Simulated sensor — Qt + C++ lab");
    auto *layout = new QVBoxLayout(&window);
    auto *status = new QLabel("Stopped", &window);
    auto *reading = new QLabel("No readings yet", &window);
    auto *start = new QPushButton("Start", &window);
    auto *stop = new QPushButton("Stop", &window);
    layout->addWidget(status);
    layout->addWidget(reading);
    layout->addWidget(start);
    layout->addWidget(stop);
    auto *sensor = new Sensor(&window);

    QObject::connect(start, &QPushButton::clicked, sensor, &Sensor::start);
    QObject::connect(stop, &QPushButton::clicked, sensor, &Sensor::stop);
    QObject::connect(start, &QPushButton::clicked, status, [status] {
        status->setText("Running");
    });
    QObject::connect(stop, &QPushButton::clicked, status, [status] {
        status->setText("Stopped");
    });
    QObject::connect(sensor, &Sensor::readingChanged, reading,
                     [reading](int sequence, double temperature) {
        reading->setText(QString("Reading %1: %2 °C").arg(sequence).arg(temperature, 0, 'f', 1));
    });
    window.resize(360, 180);
    window.show();

    // Optional automated smoke check; ordinary launches stay interactive.
    int received = 0;
    bool valid = true;
    const bool smoke = app.arguments().contains("--smoke-test");
    if (smoke) {
        QObject::connect(sensor, &Sensor::readingChanged, &app,
                         [&received, &valid, stop](int sequence, double temperature) {
            ++received;
            valid = valid && sequence == received && temperature == 20.0 + sequence;
            if (received == 2) {
                stop->click();
            }
        });
        start->click();
        QTimer::singleShot(2200, &app, [&app, &received, &valid, status, reading] {
            app.exit(valid && received == 2 && status->text() == "Stopped"
                     && reading->text().startsWith("Reading 2:") ? 0 : 1);
        });
    }
    return app.exec();
}

Build again, then launch ./build/dashboard with desktop display access. Click Start: the first sample arrives after about 500 ms. Stop freezes the reading; Start resumes the sequence. Closing the window exits the application by default. The final block is an optional smoke check; ignore it on your first reading of the program.

auto *sensor asks the compiler to deduce the pointer type, still statically checked. The window is a local value; its children are allocated with the window as their parent. The window owns the sensor, buttons, labels, and installed layout; the sensor owns its timer. When main exits, the window destructor releases this child tree. A raw pointer variable by itself owns nothing. For non-QObject resources, prefer values or an appropriate RAII owner such as std::unique_ptr; avoid giving two independent owners responsibility for deleting the same object. Qt object trees and ownership.

The label update lambda captures the label pointer by value. That copies the address, not the QLabel. Using that same label as the connection context ensures Qt disconnects this callback when the label is destroyed. QString::arg substitutes values into the display text. The Sensor knows nothing about labels: its notification can drive a UI, logging, or another receiver.

Try it and verify

  1. Connect readingChanged to a second lambda that logs each sample. Confirm both receivers run.
  2. Add a Reset button connected to your reset method. Verify the first sample after resetting has sequence 1.
  3. Click Start repeatedly. The existing timer restarts; you should not accumulate duplicate connections because connections are created once during setup.
  4. Close while running and reopen. The new process begins with fresh state.

5. Read a real Phusion dialog with a checklist

Start at /home/mauricio/1playground/phusion. Use symbol searches so these instructions survive line-number changes:

cd /home/mauricio/1playground/phusion
rg -n 'DialogViewTraces|setupUi|delete ui|setAdditionalMessageHandler' spatialexplorer/dialogviewtraces.*
rg -n 'class DialogSettingsLocal|Q_OBJECT' spatialexplorer/dialogsettingslocal.h
rg -n 'connect\(' spatialexplorer/dialogsettingslocal.cpp
rg -n 'int main|return rover.exec' rover/rover.cpp
rg -n 'int main|exec\(' spatialexplorer/spatialexplorer.cpp
  1. Read dialogviewtraces.h: identify its base class, constructor, destructor, and Ui pointer.
  2. Open dialogviewtraces.ui: find the plainTextEdit object name. The XML describes the widget tree.
  3. Read the constructor in the cpp: setupUi builds that tree, then C++ populates and connects behavior.
  4. Read the destructor: deleting the generated Ui helper differs from deleting its widgets, which have Qt parents. The helper itself is not a QObject.
  5. Find setAdditionalMessageHandler. This is a stored C++ callback, not a Qt connect. Notice that the destructor explicitly clears it. Qt’s automatic connection cleanup does not apply to arbitrary callback storage.
Existing code is a reading exercise, not a universal template. This dialog calls processEvents and even comments on side effects. Processing nested events can re-enter application code before the current operation is finished. Do not copy this as the solution to a frozen UI; keep callbacks short and separate long work.

6. Extend the lab, then pick a Phusion direction

Capstone: a useful simulated sensor monitor

  1. Add a temperature threshold with QDoubleSpinBox. Store the threshold separately from the display string.
  2. Show HOT or OK from each incoming numeric reading. Test equality at the threshold and changing the threshold while stopped.
  3. Keep the last 20 readings in a value container. Drop the oldest when adding the 21st.
  4. Show the count, minimum, and maximum. Define the empty-state display before coding.
  5. Add a clear-history button and verify that acquisition continues after clearing.

Completion check: the dashboard remains responsive; Start/Stop/Reset behavior is intentional; empty history is handled; equality is tested; closing while active exits cleanly. Explain which objects own memory and which variables merely borrow it.

Keep learning C++ alongside every feature

When you meet a new declaration, ask: value or identity? copy or borrow? who destroys it? can this callback outlive what it captures? Then learn the syntax you need: constructors and destructors, const correctness, references, RAII, standard containers, iteration, and lambdas. Follow those with error handling, smart pointers, and move semantics. Qt provides the practical reason to learn these; the language rules explain why the result works.

When something breaks

SymptomFirst check
Undefined reference to vtable or a custom signalCheck Q_OBJECT, AUTOMOC, header inclusion in the target, and that declared virtual functions/destructors have definitions. Reconfigure and rebuild.
No timer outputIs the timer still alive, started, and serviced by a running event loop?
Frozen windowLook for long loops, sleeps, or blocking I/O in a GUI callback. A timer does not make its callback run on a worker thread.
Crash after closing a dialogCheck captured references/raw pointers and callbacks registered outside QObject::connect.
Callback runs twiceLook for repeated connect calls, especially inside Start handlers.
Cannot find ui_*.hCheck the .ui filename, AUTOUIC, target sources, and generated include name.
