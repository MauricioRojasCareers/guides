Time synchronization and timestamp integrity

LiDAR points, IMU samples, GNSS poses, and camera exposures only align when their timestamps describe the same instant in a known time scale. “The clock looks right” is not enough.

First, name every clock

GNSS receiver time

Provides absolute time and leap-second context. It becomes trustworthy only after the receiver reports an acceptable time status.

PPS

A precise physical edge once per second. PPS supplies the boundary; a message stream supplies which second it was.

System clock

Linux CLOCK_REALTIME. Calendar time can step or slew and is used by files, logs, and ordinary wall-clock timestamps.

Monotonic clock

Elapsed-time clock that does not jump when calendar time is corrected. Use it for timeouts and durations.

RTC

The battery-backed hardware clock used to seed time across boots. It is not the same as a NIC PTP hardware clock.

PHC

A PTP hardware clock attached to a timestamp-capable NIC, often visible as /dev/ptpN.

Three different questions: synchronization asks whether clocks agree; timestamping asks where and when an event received its timestamp; alignment asks whether sensor timestamps map to the same time scale and physical event.

  • Nav::initialize() listens for parser time and waits for consecutive fine-time reports before emitting timeEstablished.
  • Rover accepts the best time source and calls HostClock::setSystemTime() for GNSS time.
  • HostClock slews offsets below 10 ms with adjtime(), steps larger offsets with settimeofday(), and may update the RTC when the difference exceeds 10 seconds.
  • A very large correction can trigger a controlled Rover restart so dataset names and startup-time assumptions are rebuilt using corrected time.
  • PtpManager enables PTP only for configured LiDARs that require or select it, maps sensor addresses to NICs, writes the embedded ptp4l.conf, and starts the PTP processes.
  • Nav::slotSetOffsetUtcToGps() checks the receiver's GPS/UTC leap-second offset against the time library.
Clock-changing commands are disruptive. Never run date -s, hwclock --systohc, phc_ctl ... set, or an extra time daemon on a recording or production Rover. Stepping a clock can reorder logs and invalidate acquisition assumptions.

Vocabulary that prevents mistakes

TermMeaningSymptom when wrong
OffsetDifference between two clocks at an instant.Consistent displacement between sensors.
Drift / frequency errorRate at which offset changes.Alignment worsens through the mission.
JitterShort-term variation in timestamp or delivery timing.Noisy timing even when average offset is small.
LatencyDelay between physical event, timestamp, transport, and processing.Stable or load-dependent lag.
StepImmediate clock jump.Time goes forward or backward abruptly.
SlewGradual correction by changing clock rate.Offset converges without a discontinuity.

Observe before changing

These are read-only diagnostics on a designated development Rover:

date --iso-8601=ns
timedatectl status
hwclock --show
ls -l /dev/pps* /dev/ptp* 2>/dev/null
find /sys/class/net -maxdepth 2 -name ptp -o -name device
ethtool -T ethsensor0
ps -ef | grep -E 'ptp4l|phc|rover'
journalctl -u phoenix-rover --since '10 minutes ago'
  1. State the failing relationship: camera-to-GNSS, LiDAR-to-IMU, PHC-to-GNSS, or system-clock-to-GNSS.
  2. Record the time scale and clock source for each endpoint.
  3. Check physical signal presence and polarity before tuning software.
  4. Check receiver time status and leap-second information.
  5. Check NIC timestamp capability and map each interface to its PHC.
  6. Read PTP servo state, offset, frequency adjustment, and path delay over time.
  7. Compare behavior at boot, after lock, under load, and after reconnect.
  8. Preserve logs and configuration before changing thresholds.
Interpret the pattern: constant offset suggests scale, epoch, cable, or configured-delay error. A ramp suggests frequency drift or a servo not locked. Random spikes suggest scheduling, buffering, network asymmetry, or timestamping too late in the path.

Code reading and exercises

  1. Read common/timepoint.h/.cpp; list every supported time scale and named conversion.
  2. Trace ParserNav::time into Nav::timeEstablished, then into HostClock.
  3. Explain why Rover waits for fine time and why it treats small and large offsets differently.
  4. Read rover/ptpmanager.cpp beside rover/ptp4l.conf; write down the source, sink, interface, transport, and delay mechanism.
  5. Inspect i210_phc_sync/ and draw where GNSS serial data and PPS enter the system.
  6. Given an offset plot, classify it as constant offset, drift, jitter, or step before proposing a fix.

Proven references

  • Linux kernel: PPS explains how precise edges become timestamped /dev/ppsN events.
  • Linux kernel: PTP hardware clocks explains PHCs, external timestamp events, and PPS integration.
  • linuxptp: ptp4l is the authoritative option and time-scale reference for the daemon Rover launches.
  • linuxptp: phc2sys teaches the standard PHC/system-clock relationship, useful context even though Rover also has custom i210_phc_sync.
  • linuxptp: pmc shows how to query PTP datasets and port state.
  • NIST time and frequency glossary is a dependable reference for offset, stability, UTC, and related terminology.
