Serial communication from wire to parser

Serial debugging becomes manageable when you separate electrical transport, Linux device identity, port configuration, byte framing, protocol parsing, and application state.

Debug one layer at a time

LayerQuestionTypical evidence
PhysicalAre power, ground, voltage levels, TX/RX, and flow-control wiring correct?Schematic, cable pinout, oscilloscope or logic analyzer.
USB / kernelDid Linux enumerate the adapter and load its driver?dmesg, lsusb, sysfs.
IdentityWhich stable name represents this physical device?/dev/serial/by-id/ symlink and udev properties.
Port settingsDo baud, data bits, parity, stop bits, and flow control match?Configuration and stty.
BytesAre bytes arriving intact and fast enough?Hex capture, byte counts, overrun/error logs.

SemanticsDoes the decoded packet make sense for state and time?Parser output and protocol specification.

  • common/abstractconnection.* wraps either QSerialPort or QTcpSocket. A port string such as /dev/...:115200 carries the baud rate.
  • Serial defaults are 8 data bits, no parity, one stop bit, and no flow control: commonly called 8N1.
  • findSerialPort() searches stable device names and can infer common baud rates embedded in names.
  • rover/nav.cpp identifies supported navigation receivers from /dev/serial/by-id.
  • rover/ioport.cpp shows deferred initialization, raw RX/TX logging, buffering incomplete packets, parsing complete packets, and reconnecting after an error.
  • rover/microcontroller.* shows a high-rate case where blocking the reader can lose IMU samples.

The asynchronous Qt pattern

QSerialPort *port = new QSerialPort(this);
port->setPortName(devicePath);
port->setBaudRate(115200);
port->setDataBits(QSerialPort::Data8);
port->setParity(QSerialPort::NoParity);
port->setStopBits(QSerialPort::OneStop);
port->setFlowControl(QSerialPort::NoFlowControl);

connect(port, &QSerialPort::readyRead, this, [this, port] {
    mReceiveBuffer.append(port->readAll());
    parseAllCompleteFrames();
});
connect(port, &QSerialPort::errorOccurred, this,
        [this, port](const QSerialPort::SerialPortError error) {
            if (error != QSerialPort::NoError)
                handlePortError(port->errorString());
        });

if (!port->open(QIODevice::ReadWrite))
    throw std::runtime_error(port->errorString().toStdString());
  • readyRead means “some bytes are available,” not “one complete packet arrived.”
  • One callback may contain half a packet, one packet, or many packets. Keep a persistent receive buffer.
  • A robust parser finds synchronization, validates length and checksum, consumes valid frames, and retains an incomplete tail.
  • On corrupt input, make forward progress: discard enough data to search for the next sync marker without looping forever.
  • write() queues bytes. If completion matters, observe bytesWritten; do not assume the peer received or accepted them.
  • Blocking waitForReadyRead() can be reasonable in a dedicated worker thread, but not in an event-loop thread that must handle timers and other devices.

Observe-only checklist

ls -l /dev/serial/by-id/
lsusb
dmesg --follow
udevadm info --query=property --name=/dev/ttyUSB0
stty -F /dev/ttyUSB0 -a
lsof /dev/ttyUSB0
journalctl -u phoenix-rover --since '10 minutes ago'
Start here: photograph or record the cabling, device identity, symlink target, configured baud/framing, owning process, and relevant logs. These commands do not intentionally change the device.
Opening a serial port is not automatically safe. QSerialPort uses exclusive access, and terminal programs can steal the port from Rover. Sending arbitrary bytes can reconfigure a GNSS receiver, enter a modem command mode, trigger firmware behavior, or corrupt a capture. Stop the service only on an approved development unit and only after preserving its state.

Safe practice exercises

  1. Use a USB serial loopback adapter disconnected from Rover hardware. Identify it through /dev/serial/by-id.
  2. Write a tiny Qt console program that buffers newline-delimited input and survives split/multiple reads.
  3. Replace newlines with a binary frame: sync word, fixed-width length, payload, checksum.
  4. Feed the parser recorded chunks of every possible boundary size. Verify that chunking does not change results.
  5. Simulate unplug/replug and verify one reconnect timer, no duplicate connections, and no stale pointer.
  6. Only then trace AbstractConnection, IoPort, Nav, and MicroController on a development Rover.
